# One deterministic sim for development and the demo

Status: approved by the owner 2026-10-18 (design and the decisions below). Built one step at a time (section 6).

## Goal
Owner, 2026-10-18: "we should have one deterministic sim for development. otherwise if we have bug in wall mode it will be very hard to reproduce in locked step mode."

Owner, later the same day: avoid two execution routes; one deterministic run for simulation, the demo and the rest. Operators may click in the GCS app during a run, but each action must be fixed in time so a bug is easy to reproduce.

So lockstep (`deterministic_demo_eval.md`, `lockstep_fleet.md`, `lockstep_contracts.md`) becomes the only way anything simulated runs: development, evals and the simulated demo. Wall time is left for real hardware only, with the same product code on the wall clock (the `RuntimeTime` port, `runtime_time.py`). Two properties must hold together:
- **Realistic:** the timing, ordering, loss and noise effects that cause bugs in wall mode, and on hardware, also happen in lockstep.
- **Repeatable:** the same code, manifest and seed give the same digest, as the 5-run matrix proves (with every model off, seed 1: `d54e57b2…` since step 12's base `705abab2`; section 6).

The way to get both is the one established deterministic simulation testing uses: every source of chaos is a model that draws from the run seed, in sim time.

## Established practice (checked first)
- **FoundationDB** runs the whole cluster single-threaded in simulation, with machine, disk and network faults injected on purpose, at short failure intervals and heavy load, and tens of thousands of runs each night. A failure is rerun by its seed ([testing](https://apple.github.io/foundationdb/testing.html)). Its `BUGGIFY` macro also makes product code take rare paths (slow, early timeout) when the seed says so (Will Wilson, Strange Loop 2014).
- **TigerBeetle's VOPR** runs the real code with a seed that also picks the fault parameters (packet loss, reordering, partitions, storage faults). Seed plus git commit reproduces a failure exactly. It runs all the time on 1024 cores ([safety](https://docs.tigerbeetle.com/concepts/safety/), [VOPR](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md)).
- **Antithesis** runs unchanged software in a deterministic hypervisor and injects network faults (latency, partitions, clogs), node faults (pause, kill), clock jumps and thread pauses throughout the run, interleaved with the workload ([fault injection](https://antithesis.com/docs/concepts/fault_injection.md)).
- **Swarm testing** (Groce et al., ISSTA 2012): each run turns a random subset of fault kinds on, instead of all of them every time. It finds more bugs, because some bugs need a fault to be absent.

What we take: (1) every effect is seeded and in sim time; (2) the seed also picks which effects are on and how strong (swarm); (3) faults run during the whole mission, then heal, and the mission must still finish (safety and liveness); (4) a failure is its seed plus commit; (5) many seeds, not one long run. What we do not copy: a hypervisor. Our baton already makes the threads deterministic; the models plug in around it.

## 1. The gap: what wall mode has that lockstep lacks
Lockstep today, from the code:
- **Links are perfect.** SITL to NavPy arrives in the same tick; NavPy to SITL is admitted by the same tick's reply (`COMMAND_ACK` in frame k+2); NavPy to NavPy goes NavPy, autopilot, router, autopilot, NavPy; it measured 4 ticks for every pair at step 10f-1 (`deterministic_demo_eval.md:28`), but backlog, carry-over and the autopilot's parse budget can change it, so the contract is reproducibility, not a hop count (`lockstep_fleet.md:124`). Queues never drop, and the coordinator adds no delay, jitter, loss or bandwidth model (`lockstep_fleet.md:110,118`; `coordinator_router.py`). Only the caps 0xFFFF bytes per port per reply and `min(fifo, space, 10000)` per io tick exist (`lockstep_contracts.md:82`); since step 3 SITL's own line rate and byte loss can apply inside each SITL.
- **Compute takes zero sim time.** `monotonic`, `perf_counter` and `thread_time` all return `t_k` (`lockstep_runtime.py:52-64`; `deterministic_demo_eval.md:164`). A process can never fall behind, stall or starve, unless a step-4 freeze or CPU budget caps its baton handoffs (section 2).
- **Thread order is FIFO and switches only at primitives.** Runnable threads run first-in first-out; timers in `(due, park seq)` order (`lockstep_contracts.md:46`). Wall threads are preempted by the OS and the GIL every 5 ms. Since step 6, `thread_order` makes the order seeded (section 2).
- **Phase order is fixed.** Without a reader budget the lockstep reader yields after every packet, so a woken consumer always runs before the next packet (`ReaderService.after_packet`, `lockstep_bus.py:71-73`; with a budget it drains, todo 65's fix); the wall reader yields once per batch (`reader_batch.md`). An input on a waiter's deadline tick always beats its timeout (`lockstep_contracts.md:39-45`). Wall mode has neither guarantee. Since step 6, `reader_budget` and `timers_first` can lift both (section 2).
- **The camera has no latency** unless `camera_frames` is on (step 5). Without it, NavPy renders the frame from the pose it just received (`deterministic_demo_eval.md:100`).
- **SITL noise is one fixed sequence, not the seed** (before step 2, which seeds it and sets wind; section 2). Checked in the firmware locked then (`2dbd7e38dd`): noise comes from glibc `random()`/`rand()` (`AP_Math.cpp:343-346`, `SIM_Aircraft.cpp:356-375`), and nothing calls `srandom` (only Lua's `math.randomseed`, `lmathlib.c:282`), so every SITL start uses glibc's default seed 1. `get_random16` has fixed seeds 1234/76542 (`AP_Math.cpp:332-338`). No `SIM_` seed parameter exists; the branch does not touch noise. Default ArduPlane noise is on (`SIM_BARO_RND` 0.2, `SIM_ARSPD_RND` 2.0, `SIM_DYN_GYR_RND` 0.1, `SIM_DYN_ACC_RND` 0.3); GPS noise, mag noise and wind are 0. Lockstep set no `SIM_WIND_*` or noise parameter. No deployed Lua script calls `math.random` (grep of `scripts/lua`), so the main-thread draw order is fixed.
- **Missing features.** Lockstep refuses MAVFTP, has no ESP32 HTTP simulator, and has no frontend (`deterministic_demo_eval.md:63-77`; `lockstep_slice.md:61`).

Two kinds of wall bugs need different answers:
- **Real-world bugs:** freezes, lag, loss, jitter, latency, ordering. Hardware has them too. Lockstep must model them.
- **10x artifacts:** a SITL slowed to 6.7x, cadences divided by 10, the GC pause being 10x longer in sim time. Hardware runs at 1x and does not have them. The model reaches them only through a stress profile (below), not the default.

One limit stays: the baton switches threads only at primitives (locks, queues, sleeps), so a race between two bytecodes with no primitive between them cannot happen in lockstep. Seeded thread order (section 2) covers races at primitives, which is where our documented races are (todo 31, 45). A bytecode-level race needs a code review or a wall run; it is listed as a known gap.

## 2. Seeded realism models
All models are SITL's own features set by parameter (steps 2 and 3), or live on the coordinator side or in the participant loop, never in product code. Each draws from its own stream, seeded by SHA-256 of `domain:run seed:model:link or ordinal` as participant seeds are, with values from `random()` only, so turning one model on or off does not shift another's draws. One exception: inside the SITL, turbulence and sensor noise share the firmware's one glibc `rand()`, so turning turbulence on shifts the noise draws after it (todo 81); an A/B of wind at one seed changes the noise too. Byte loss is the coordinator's radio model since step 3's round 6 (`radio_link.py`, `sitl_models.py:27-30`), on its own stream, so it shifts no SITL draw. Delays are counted in ticks (about 20 ms; `t_k` is the SITL's `source_us`). Every delayed, dropped or reordered packet keeps a journaled disposition, as the gates require today (`lockstep_fleet.md:196`), and a byte the radio model loses is journaled with the packet it broke (the `radio` list: `broken`, and `false` for a frame the router's framer parsed out of a broken one); a missing router copy or delivery still fails. With every model off, the digest must equal the documented `none` baseline (section 6).

A **profile** (`src/navpy/sim/lockstep/sim_profiles.json`, chosen with `--sim-profile`, default `hw`) gives each model's range. Per seed, the swarm step draws which models are on (each on with probability 0.5 by default) and a value inside each range. The draw is recorded in `input_manifest.json` (`run_options.sim_profile`), not in the journal. A model joins the file in the step that builds it, so until then no profile lists it.

**Faults** are scheduled events in the same profile, drawn per seed, and healed before the mission's last phase (liveness). Built in step 7 (`fault_schedule.py`, `coordinator_faults.py`, `radio_cuts.py`): each is a swarm-drawn model of `hw`, on in half the seeds, at most one of each kind in a run and one at a time with its recovery time:
- link drop: one radio endpoint, a SITL's serial1 or the backend's router device, at 100% loss for 1-10 s (cut at the coordinator's router seams, each packet journaled `radio_fault`);
- late heartbeat: a freeze long enough to pass a liveness timeout, 7.5-10 s. The first design's 1-3 s passes none: the peer silence and the backend's companion status both take 5 s, and the silence is certain only past 7 s (`SILENCE_PROOF_S`: one check period and a delayed timer more);
- NavPy restart: the coordinator stops a participant and respawns it with `generation + 1`, which `REGISTER` already carries (`lockstep_contracts.md`, Ownership);
- radio partition: one UAV hears no peer for 2-20 s, and its link to the backend stays up.

A fault's clock starts at a mission phase, not a sim time, as the timeline moves with the wind and the line rate: the launch, or the first check-in for a partition. Each is journaled when it starts and heals, with its id and recovery deadline: 5 s after the heal, one heartbeat TTL (`PEER_RECOVERY_S`), or 15 s after a respawn (`RESTART_RECOVERY_S`: at most 4.3 s measured to the new generation's first flow line, one heartbeat TTL for its peers to meet it, the rest margin). Everything heals at the latest at the first confirm request, and a restart starts only until every UAV has checked in, so the approval and final approach run with no fault active and no NavPy coming back. That is narrower than section 1's "during the whole mission": those phases need a recovery assertion first (todo 188). `stress` has no faults yet, so seed 40 is judged by its gates with nothing on top (todo 189). A run with scheduled faults logs at DEBUG, so a first meeting of two peers across a fault shows in the receiver's roster (`Peer N admitted`), where a delivery shows only that it reached the NavPy; every other run stays at INFO and keeps its digest. A silence of a peer ends only with the receiver's own line, whether it began by expiry or at a check-out, which the roster takes with no line of its own (`Actor N checked out` is `SwarmPresence`'s).

The firmware RNG patch: an env var `NAVPY_STEP_RNG_SEED`, set per instance from the run seed and sysid, and `srandom(seed)`/`srand(seed)` once in SITL start, before any sensor draw; also re-seed `get_random16` (its output depends on one 16-bit half only, so just seed bits 17-31 reach it; it feeds GPS jamming, compass calibration and temp-file names, none used in our runs; todo 81). An env var, not a `SIM_` parameter, because parameters load after the first draws and would persist in `eeprom.bin`. It is a firmware branch change and a new `lockstep_firmware.lock.json`. Built in step 2 as `95d96adbde` on `2dbd7e38dd`: `HAL_SITL::run` calls `NavPyStep::seed_random()` first; the value must be decimal 1..2^32-1 and is refused outside serial-step mode; unset changes nothing. Each SITL's seed is `1 + floor(r * (2^32-1))`, with `r` from the `sensor_noise` stream `sitl.<sysid>`, set while noise or wind is on; the seeds and the profile's SITL parameters are in `input_manifest.json` (`sitl.rng_seeds`, `sitl.profile_parameters`).

## 3. Reproducing a wall bug in lockstep
Options:
- **A. Record and replay a wall run's schedule.** Record each packet's measured delay and the thread switches, then force them in lockstep. Thread switches cannot be recorded from Python without heavy tracing, and the wall run is at 10x, so its delays do not map to 1x sim time. Large and incomplete.
- **B. Fit a profile, then search seeds.** A tool reads the wall run's logs (cadence gaps, freezes, reader lag, which messages were lost or late), sets the profile's ranges to match, and runs seeds until the failure's signature appears (the same gate fails, for example todo 65's observation-gap gate or `NAV_FAIL: no_detection` on any UAV; coverage is triage, not a gate, `eval_gcs_demo_cadence.py:42-44`). The found seed is then a permanent regression seed.
- **C. Write the fault by hand.** From the wall log, write a fault event at the time and place seen (for example a 740 ms freeze of UAV 3 at NAV + 0.5 s). Fast when the log names the cause.

**Recommended: B, with C as the first try when the log already shows the cause.** Both end in a seed (plus, for C, a fault file) that fails the same way every run. If neither reproduces the bug within the search budget (say 200 seeds), it is logged as an **unreproduced bug** in `architecture_todo.md`, with the possible causes: a profile that does not fit, too few seeds, a different mechanism, or a missing model. The sim changes only once mechanism evidence (from the wall logs or a wall rerun) shows which model is missing. That loop keeps lockstep realistic over time.

**Built in step 9 (B).** `scripts/wall_bug_logs.py` reads a wall run: each NavPy ATTITUDE's lag in aircraft time (the GCS's latest `time_boot_ms` at the NavPy's arrival, less the packet's), stalls of 200 ms or more over the median lag with their peak, rise and drain, NAV windows, and the failures the run logged (`NAV_FAIL`/`DOCK_FAILED` lines, `report.json` gate errors; a long source gap in the cadence episodes is no failure, as the wall gate measures wall time). `scripts/wall_bug_fit.py fit` fits a profile; `search` runs seeds, as the seed sweep does, until one fails, confirmed by a rerun at one digest, with a failure kind the wall run had, read from the confirmed run. Before choosing the model, look at the stalls' shape: a lag that jumps at once and drains is a NavPy that read nothing (`process_freeze`); one that grows slower than aircraft time is a reader that kept receiving while it fell behind (`reader_lag`).

A found seed **reproduces** a wall bug; it fails until the bug is fixed, so it is not a regression seed (those must pass, section 4). It becomes one once the fix makes it pass. A reproduction shows that the fitted model can cause the wall's failure kind, not that it was the wall's only cause.

## 5. Driving it live: the app, the demo and recorded actions
The demo and daily development use the same lockstep run, watched and driven from the GCS app.

- **Pacing to 1x.** The coordinator sleeps after each tick until `wall_start + t_k`. It sits where host delays already sleep (`LockstepCoordinator._reply`) and stays out of the manifest, as host delays do, so the digest does not change. If the PC is slower than 1x the run runs slower; that is safe while each tick ends inside the SITL's 30 s reply deadline (below), and ticks take 8-20 ms of wall time. The 3-UAV run is 1.6-1.9x faster than real time on a quiet PC, but 0.98x with host delays and 0.77x under CPU load (`deterministic_demo_eval.md:31`), so the demo PC runs nothing else. Pause is not in v1: the SITL waits at most 30 s for a reply (`STEP_DEADLINE_US`, `lockstep_wsl_sitl.py:63`).
- **A live relay.** The backend runs in-process with no socket (`lockstep_asgi.py:1`). A relay process outside the baton serves the app on the slot's ports:
  - `/ws/telemetry` from the backend broadcasts the coordinator already journals in each `DONE` (`event_sink.py:5-6`). Watching never enters the run.
  - every REST request is forwarded into the run, and its response comes back from the `DONE` of the tick its handler finishes in (`lockstep_contracts.md`, ASGI).
- **Every request is an input, reads too.** Some reads talk to the vehicle: `GET /api/vehicles/{id}/params` reads parameters over MAVLink (`routes/params.py:18-30`), and `GET .../fence` downloads the fence (`routes/missions.py:122-142`). So no request is assumed harmless.
- **The wire already exists.** The backend takes typed operator inputs: `OperatorRequest{target, id, payload}` with payload `{"kind": "http", "method", "target", "json"?, "deadline_s"?}`, and `OperatorCancel{target, id}` (`coordinator_types.py:175-185`; `src/gcs/backend/lockstep/requests.py:1-20`). Each request runs in its own cancel scope; a cancel ends exactly that request; a request past its sim-time `deadline_s` ends the same way; a response stands, so a cancel after it does nothing. Cancels are delivered before requests in a tick (`participant_loop.py:9-11`). The target carries the query string. Headers and non-JSON bodies are not carried; step 10's inventory says whether any route needs them, and the payload grows only then. Step 10 found that none does (`gcs_request_inventory.md`), so the HTTP payload stays; manual control, though, is a WebSocket input the wire does not carry (todo 240).
- **How an action is fixed in time.** The coordinator owns admission. In tick k's operator phase (`OperatorPhase.run`, `coordinator_operator.py`) it takes, in one step, everything the relay has received so far, and puts them in one admission order, scripted items first, then relay items in arrival order. Each new request gets its request id from one counter shared with the scripted operator. A cancel keeps the id of the request it cancels. A cancel for a request taken in the same step (not yet delivered) is resolved by the coordinator: the request is never delivered, its handler never starts, and the coordinator answers `{"cancelled": true}` for it. The tick's journal record holds the whole admission (every item, delivered or not, and any answer the coordinator gave), so the digest covers it. This matters because cancels are delivered before requests in a tick. They are delivered as tick k+1's inputs (`deliver_operator_requests`, `coordinator_operator.py`). The journal keeps them in the encoding the TICK already carries (TICK hashes are journaled, `deterministic_demo_eval.md:25`), so they are in the digest. A test changes one action (its tick, order, payload or a cancel, including the payload of a suppressed request) and the digest must change.
- **The action file** is that list: each admitted request and cancel with its tick and id, scripted and human alike. Replay feeds only the file and turns the script off, so nothing is sent twice.
- **Responses.** A response returns in the `DONE` of the tick its handler finishes in, as `{"status", "body"}`, `{"cancelled": true}` or `{"deadline": true}`, matched by id; completions may come back in any order. The relay sends each to the browser connection that asked. A browser that closed or reloaded gets nothing: the relay logs it and sends no cancel, because a disconnect is not an operator action. Only an explicit abort becomes a cancel. Tests: two slow MAVLink reads overlapping, completions out of order, a disconnect mid-request, a cancel before dispatch, during MAVLink work and after the response.
- **Replay.** A bug report is the commit, the manifest with seed and profile, and the action file. The replay runner needs no relay and no browser. It gives the same digest, and it runs as fast as the PC allows. "Stop at tick N" means the replay ends at tick N and writes its journal, logs and a state snapshot; there is no live pause in v1. A click lands on the tick the run is at when the coordinator takes it, not the frame the operator saw; replay is exact either way.
- **No app-side clock decides anything sent to the run.** The confirm card counts down on `Date.now()` and auto-approves or denies at zero (`TaskConfirmCard.jsx:55-88`). At a 0.8x run the operator would get less sim time than the timeout says, so the countdown counts sim time (the telemetry `ts`). The armed token is checked against `Date.now()` (`useFullParams.js:454,463`) and would always look expired, because sim time starts 2026-01-01; it must use the backend's `ts`. Fetch timeouts (20 s and 45 s wall, `usePlanningApi.js:10-11`) become the request's sim-time `deadline_s`; the browser's own abort only frees the page and sends no cancel. Step 10 audits every `Date.now`, `setTimeout` and `setInterval` in the frontend that can lead to a request, and the backend code behind every request supported in simulation. A request not supported in simulation is refused (`501`, hardware-only) and the refusal is recorded like any answer. Map animations on wall time are display only and stay.
- **Launcher.** A lockstep run with the app needs frontend and relay ports from its slot, a change to owner ruling 4 ("the eval band, no frontend", `lockstep_slice.md:61`), and todo 55 fixed so `gcs_stop.py` can stop it.
- **As built (step 11).**
  - `--app` (with `--lockstep`, Windows host only, as the fleet is) starts the relay (`scripts/lockstep_app_relay.py`, its wire format in `lockstep_app_wire.py`) on the slot's backend port and Vite on its frontend port; ruling 4 changes for app runs only.   - Admission is `coordinator_admission.py`, run in the operator phase (`OperatorPhase`, `coordinator_operator.py`). Relay items wait in the relay until the backend is ready. A tick journals an `admission` note only when it took relay items, so a scripted-only run keeps its digest. Each note lists the script's and the relay's items, payloads as hashes, with any answer the coordinator gave. A script's cancel for a request it sent in the same step is resolved the same way (the script gets `{"cancelled": true}`) and journals a note too; no script cancels today.

  - The action file is `lockstep_actions.jsonl` in the run directory: one line per admitted request or cancel, with tick, source (`script` or `relay`), id, target and the request's payload.

The action file now ends with an `end` line: the tick the operator returned at, so the replay ends where the run did.
