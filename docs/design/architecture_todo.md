10. **Late-deny window** (found by the flow-runner review, 2026-10-08; UNVERIFIED in flight).

## Found while fixing the demo eval (2026-10-12; predate the fix)
26. **Mission upload truncates coordinates.** The planner encodes lat/lon as `int(degrees * 1e7)` (`src/gcs/backend/planner/mission_items.py:66-67,91-92,138-139,168-169,187-188`), so a download and re-upload moves some points 1e-7° (about 1 cm) south or west. Use `round()`. The demo eval's scenario stores only values that encode exactly.
27. **NavPy and the GCS number NAV waypoints differently.** NavPy counts the appended default-delivery-hub row (`src/navpy/plugins/vehicle/ardupilot/nav_waypoints.py:15-22`); the GCS parser drops it (`src/gcs/backend/mission_validator.py:106-111`). A POI ordinal past the track names the hub in NavPy and nothing in the GCS. The demo eval rejects such ordinals; check every other path that sets `AAS_TARG_WPS`.
28. **Slot 0 runs on the shared SITL templates** (`~/ardupilot/{1,2,3}`), so its param writes and mission uploads change what every other slot clones. Between 06:42Z and 08:52Z on 2026-10-12 the template missions changed from 7/5/5 to 6/2/6 track rows, which broke the demo eval. The eval now uploads its own missions; step 3 of `docs/design/deterministic_demo_eval.md` gives each run a fresh root.
29. **A UAV at the delivery hub advertises the hub as a new task.** In sim, the hub fallback places a dock at the hub (`src/navpy/core/flow/fallback_mission_navigation.py:64`) so the UAV can approach it. The UAV then detects that dock and offers it to the swarm; the owner flies it first and asks again to confirm its own POI. With the 6/2/6 missions, UAV 2 reaches the hub early, so the demo eval fails with "vehicle requested more than one confirmation round" (`.logs/step1-wall-a`, `-b`). Owner's intent: a UAV that finds no delivery dock flies to the home dock (DDH), acquires it by vision, asks confirmation and parks if confirmed; the home dock is never a swarm task. Behavior after a rejected home dock is undecided.
30. **The planner balances search paths only at whole-strip boundaries** (`assignStripsEqualDistance`, `src/gcs/frontend/src/utils/trackGenerator.js:86`). Requirement: every UAV gets an equal search path. On a diamond-shaped area with 7 strips (224/673/1121/1427/1123/674/225 m), today's demo missions got 2635/1430/2636 m tracks, so UAV 2 finished early and homed (see 29).

37. **The RuntimeTime lint is a first net, not a proof.** `tests/guards/runtime_time_lint.py` resolves names statically. Twenty Codex review rounds of step 8 kept finding further edge forms: annotation and alias shapes for identity-hashed sets (closed by failing on any annotation that does not resolve), and clock aliases through other binding forms (class members, subclasses, instances). None was found in product code; five dangling product annotations were fixed. Rounds 13-19 replaced shape-chasing with fail-closed rules (unresolvable annotations, the port or a host module or a datetime class held as a value, runtime identity for re-exports, a reviewed external-import inventory), yet each round still finds 3-8 new forms, mostly further library APIs and value types (round 20: more OpenCV/PyTorch members, NaN floats hash by identity, factories in the composition root). A static lint cannot be complete here; the run-twice byte comparison in step 9 is the proof. The documented limits: unannotated sets of objects, reflection and exec, and lexical-scope shadowing. The lockstep thread audit and per-tick journal (step 9) are the backstop. Reviewed external modules are boundaries the lint cannot see into; the GCS backend's `asyncio.sleep` waits (routes, `telemetry_loop.py`) are host waits that the backend participant (step 9f) must drive or replace. A runtime tripwire would close more of this: a lockstep participant fails on any host clock, thread start or entropy call.
38. **Heavy work runs on the MAVLink reader thread.** `InboundRouter.ingest` dispatches every subscription callback synchronously (`src/navpy/plugins/vehicle/ardupilot/inbound_router.py:133-135`), so any slow callback delays every later message, including attitude and position for navigation. Seen in `.logs/dock-d` (item 34). Callbacks should only copy the message and hand it to their own worker (a bounded queue or a latest-value slot), and a reader-lag measurement (receipt vs boot time) should flag a backlog. Applies on main generally, not only to the contact sensor.
39. **Under the vision law an own POI has no coordinate for the loss fallback.** `last_own_poi_geo` is now recorded before NAV (`src/navpy/core/skills/confirm/poi_presence_review.py`), but no detector fills `projected_poi_location` under the vision law; the only producer is the legacy review step (`confirmation_legacy_prep.py`). So an owner that loses its dock in CONFIRM cannot re-point at it. Needs a camera ground fix that never reaches the final approach.
40. **The sim uses truth where real flight has an estimate.** After detection, the orbit centre and the location sent to peers use `truth_poi_location`, not the camera ground fix (`src/navpy/core/skills/geo_approach/self_detected_approach.py:105-110`, `src/navpy/core/swarm/nav_network.py:170-173`, `peer_poi_notification.py:43-47`, `self_assignment_publisher.py:39-40`). And a peer's sim dock is moved to the task-message location (`src/navpy/core/skills/acquire/peer_approach_start.py:30-35`). So in sim a wrong reported position can never cause a miss. Owner rule (2026-10-13): before a UAV detects the dock or receives it in a task message, nothing uses waypoint dock info; the home dock (DDH, `fallback_mission_navigation.py`) reads it from the mission, pending the owner's call on whether that counts as an assignment. **Owner ruling 2026-10-13:** the home dock (DDH) is an operator-assigned exception.
41. **The roll-reversal gate fails good approaches.** It allows one sign change among commanded rolls of 10 deg or more (`scripts/eval_gcs_demo_metrics.py:26-28`, `eval_gcs_demo_limits.py:68-69`). Docked owner runs count 3: one flip at approach start and one in the last samples (`.logs/dock-e`, `.logs/peer-cam-1` UAV 1, `DOCKED` 0.15 m). Set the gate from what it is meant to catch.
42. **The demo eval reports a second confirmation, not the failure behind it.** It aborts on a second confirmation round (`scripts/eval_gcs_demo_mission.py:145-150`), but after a failed pass RESET is a fresh start and asking again is intended. The report should name the `NAV_FAIL` that caused it (`.logs/peer-cam-2`).
43. **The command-core clock guard is name-based** (`tests/guards/test_frozen_inventories.py`). It enforces the pure-vision rule (no clock in final-approach command decisions), not determinism: under lockstep every `rt` clock is the sim clock. It catches clock names, the port held as a value and injected `Callable`/`ClockPort` annotations (a frozen inventory). A clock can still reach the core through a dependency type: a callable alias such as `SourceNow` (`source_time_ports.py`), an unannotated `self._read = read` field, or a first-party clock adapter such as `NavClock` (`core/flow/nav_clock.py`) or a Protocol whose implementation reads `rt`. A runtime tripwire would close it: run the core's tests under a runtime whose clock raises.
44. **ATTITUDE history spans too little time at a high pose rate.** The vehicle keeps `ATTITUDE_HISTORY_COUNT` = 64 ATTITUDE samples (`docs/design/message_history.md`): 1.6 s at 40 Hz but only about 0.2 s at a 320 Hz stream (`src/navpy/plugins/vehicle/ardupilot/pose_streams.py:63`), below the 0.5 s capture ceiling (`src/navpy/core/perception/pipeline/real_frame_association_gate.py:78`). Pre-existing. Size the depth from the stream rate and the ceiling.
45. **A logger closed before its worker runs loses its queued lines** (found in step 9b, 2026-10-14; not fixed on the wall path). If `CacheLogWorker.close()` wins the launch gate before the worker thread enters (`src/navpy/core/kernel/logging/cache_log_worker.py`, `cancel_before_commit`), the worker is cancelled and everything queued, including "Logger closed", is never written. This is reachable on the wall path, e.g. construction rollback right after `initialize_logger` (`src/navpy/app/runtime_composition.py:110`). The strict close (`log_output_latch.close_strictly`, used by the lockstep drain flush) drains the queue in the caller; the wall close still drops it, because draining there would add lines in the rollback path and is not bounded by `CACHE_WORKER_JOIN_TIMEOUT_S`. Decide whether the wall close should write them, and bound it if so.
